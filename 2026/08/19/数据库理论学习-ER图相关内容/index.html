数据库理论学习-ER图相关内容

发表于2026-08-19|更新于2026-08-19|数据库
|浏览量:

属性

派生属性：可以由其他属性经过运算得到的属性，因而派生属性产生冗余，通常不存储;

多值属性：一个实体在该属性上会同时取多个属性值，这些值也都必须存储（比如一个人有多个手机号，手机号就是多值属性）

简单属性：原子的、不可再分的。

复合属性：可以细分为更小的部分(即划分为别的属性)。有时用户希望访问整个属性，有时希望访问属性的某个成分，那么在模式设计时可采用复合属性。

比如学生实体集Students的“家庭住址”就是复合属性，因为可以进一步分为邮编、省、市、街道。

合并冲突

根据局部应用设计好各局部E-R图之后，就可以对各个局部E-R图进行合并。合并的目的在于解决分ER图中相互间存在的冲突，消除分E-R图之间存在的信息冗余，使之成为能够被全系统所有用户共同理解和接受的统一的、精炼的全局概念模型

结构冲突：同一实体在不同的分E-R图中有不同的属性，或者同一对象在某一分E-R图中被抽象为实体而在另一分E-R图中又被抽象为属性。

名字可能一样或不一样，但对同一现实事物的结构定义（类型、键、基数）不一致。

属性冲突：同一属性可能会存在于不同的分E-R图，由于设
计人员不同或是出发点不同，对属性的类型、取值范围、数据单位等可能会不一致，这些属性对应的数据将来只能以一种形式在计算机中存储，

单位不统一

命名冲突：相同意义的属性在不同的分E-R图上有着不同的命名，或是名称相同的属性在不同的分E-R图中代表着不同的意义，

同名异义和异名同义

判断步骤

  1. 如果不改名字，只修改数据类型/主键/基数，能解决吗？
    → 能，就是结构冲突（因为结构定义错了）。
    → 不能，必须改名字，就是命名冲突。

  2. 冲突的本质是“词汇”还是“骨架”？
    → 词汇（叫什么）= 命名冲突。
    → 骨架（实体、属性、连线、基数）= 结构冲突。

    举个例子：

    • “系”在A图是属性（字符串），在B图是实体（有编号） → 这是结构冲突（因为“身份”变了）。
    • “系”在A图叫“Dept”，在B图叫“Department” → 这是命名冲突（因为身份没变，都是实体）。

ER模型向关系模型的转换规则

核心转换原则

ER模型中的三个主要元素（实体、属性、联系）按以下逻辑转换为关系模式（二维表）：

  • 实体 → 一张独立的关系表。
  • 实体的属性 → 表的列（字段）。
  • 实体之间的“联系” → 根据联系类型（1:1, 1:N, M:N），决定是把“外键”放进去，还是单独建一张“联系表”。

具体转换规则

一对多联系（1 : N）

1 的主键入 N 表。

  • 不新建表：在 N（多）端 的关系模式中，加入 1（一）端 的主键，作为外键。
  • 不需要把N端的主键放到1端。

例1

  • 业务：院系（D）与学生（S），一个学生属于一个院系，一个院系有多名学生。
  • 转换：学生是 N 端，院系是 1 端。在 学生表 S 中加入 院系表 D 的主键（院系号）。
  • 结果：S（学号，姓名，性别，院系号）。

例2

  • 业务：科室与职工，每个科室有多名职工，一名职工只属于一个科室。
  • 转换：职工是 N 端，科室是 1 端。在 职工表 中加入 科室表的主键（科室号）。
  • 结果：职工（职工号，职工姓名，科室号，住址，联系电话）。

多对多联系（M : N）

必须新建独立表。

  • 强制要求：多对多联系必须转换为一个独立的关系模式（联系表）。
  • 主键设定：该联系表的主键为 （两端主键的组合）。如果联系本身带有“时间”等能区分多次记录的属性，且同一组合可能发生多次时，应将时间属性也纳入主键。
  • 属性构成：联系表 = 两端主键（外键） + 该联系自带的属性。

例

  • 业务：病患与医生（职工中的医生）。一个病患可由多个医生诊治多次；一个医生可诊治多个病患。
  • 重点：题干特别强调“多次诊治”，意味着同一病患和同一医生可能多次就诊。
  • 转换：
    • 必须新建 就诊 表。
    • 主键不能仅为（病历号，职工号），因为同一个人找同一个医生看了两次，主键会冲突，所以必须加上 就诊时间 作为主键的一部分。
    • 最终设计：就诊（病历号，职工号，就诊时间，就诊情况）。

一对一联系（1 : 1）

随便放一端，或者独立成表（少见）。

  • 转换方式一：将任意一端的主键，放入另一端作为外键（通常放在需要频繁查询的那一端）。
  • 转换方式二：如果联系本身带有丰富的属性，也可以单独建表，但主键可以取任意一端的主键。

在考试中，如果题干出现“假设一对多联系不转换为一个独立的关系模式”：

  1. 1:N → 把 1 端主键塞进 N 端表里（不建新表）。
  2. M:N → 无视题干任何“不建表”的假设，因为多对多必须建表。这是数据库的硬性规定。

1对N，一主进多端，不用新建表；
M对N，必须新键表，两端主键加联系属性；
1对1，随便塞，哪边方便哪边来。
